# Security model

PayPilot AI is a **fake-money public portfolio simulation**. It does not accept bank credentials, cards, UPI credentials, real customer data or real payment gateways.

## Implemented controls

### Side-effect authority
- The model cannot directly execute a payment.
- LLM-only parsing cannot create a transfer/bill-payment side effect when deterministic parsing did not recognize one.
- Financial fields are validated by typed Pydantic schemas and deterministic policy.
- Only allow-listed application tools are callable; there is no raw SQL, shell, filesystem, arbitrary HTTP or browser tool.

### Authorization
- <= ₹2,000 may auto-authorize only after policy/risk checks.
- > ₹2,000 requires explicit human approval.
- User-requested confirmation thresholds can be stricter than the global threshold.
- Every authorized payment is revalidated immediately before execution.
- HIGH-risk requests are escalated to explicit human approval when otherwise      eligible; a request is blocked when the configured hard risk threshold is reached or another deterministic rule fails.
- Platform-limit, insufficient-funds, daily-limit, stale bill/destination and invalid-state failures always block execution.

### Integrity and replay safety
- Decimal / fixed-point money representation.
- Database-serialized final check-and-act boundary.
- Idempotency key + unique transaction constraint.
- Ledger mutation and final audit state commit atomically.
- Approval of an already terminal run cannot create another payment.

### Session and public-demo abuse controls
- Session IDs are generated by the server and must be valid UUIDs.
- Stateful endpoints reject missing, forged, expired or unknown sessions.
- Per-session and global agent-run limits protect model/API cost.
- Session creation itself is rate limited.
- TTL/reset removes domain rows; LangGraph checkpoint cleanup is also attempted.

### Web/API hygiene
- Exact CORS origin is recommended for deployment; wildcard credentials are not enabled.
- API state responses use `Cache-Control: no-store`.
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, restrictive referrer/permissions headers.
- Frontend CSP is included for the Docker/nginx build.
- Request logs contain request metadata/IDs, not prompt bodies.
- Exceptions returned to callers are sanitized rather than exposing stack traces/types.

### Supply-chain / packaging hygiene
- Backend container runs as a non-root UID.
- `.dockerignore` removes local secrets, DBs, caches and virtualenvs from Docker contexts.
- The release packaging script excludes `.env`, local databases/WAL files, `.venv`, `node_modules`, build output, caches and Git metadata.
- CI installs from clean dependency manifests and runs backend compile/tests plus a clean frontend production build.

## What this project intentionally does NOT claim

A public fake-money demo does not need or pretend to implement the full control plane for regulated banking. A production real-money platform would need at least: authenticated identities and fine-grained authorization, KYC/AML and fraud/risk systems, secure payment rails, managed secrets/HSM/KMS, encrypted sensitive data, audit retention policy, distributed rate limiting, migrations, backups/PITR/DR, reconciliation, regulatory controls and incident response.

The absence of those controls is why **no real financial action is connected to this codebase**.
